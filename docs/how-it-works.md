# 原理：投影、替换与准入

> 本文回答什么问题：插件到底改了什么、为什么这样改，以及那些比例和 token 数是从哪来的。
> 想先装起来，回到 [README](../README.md)；要排障、改配置或回滚，看[运维手册](operating.md)。

## 问题：每次请求都回放全部历史

DSH 每次模型请求都会回放全部历史。本机 300 个最长会话的实测聚合（`npm run --silent stats`——
不带 `--silent` 时 npm 会把 `> dsh-boost@0.3.2 stats` 横幅打进 stdout，机器解析请用 `--silent`
或直接 `node scripts/session-stats.mjs`；快照时刻 `2026-11-19T03:13:21Z`）：54,141 步、
54,088 个请求，合计 10,575,904,022 raw token。按步均值 195,340 token，按请求均值 195,531、
中位 187,681；97.01% 的输入是缓存读。工具回执是体积主体（bash 61.75%、read 22.13%、
ssh 10.01%），而下一步真正会用到的部分通常远小于回执本身。

### 收益区间与它的边界

v1 的**事前估算**区间是 **3.5%（下界）– 10.0%（理想上界）**，按 raw `totalTokens` 计；
**3.5% 不是保底**——它是设计阶段对一个 300 会话语料做离线估算得到的下界，其中替换账的
2.70% 是**上限**，不能算进任何保底。投影侧在 **300 个最长会话**上的**聚合**净额约 **0.4%**
（毛额约 0.8% 减去每请求固定开销约 0.4%，即 778 / 195,531）；它也不是每会话保底——长会话
摊薄固定开销，**短会话可能倒亏**，而 `top-300` 里没有 ≤5 步的会话。3.5% 与 0.4% 两端都是
离线估算，不是测量。

这个区间不是保证，也不是从交付的 `session-snapshot.json` 能复算出来的数字：快照按会话存了
聚合计数，也存了每个会话的 `requestTokens` / `receiptChars` 数组、`valueTransfer` /
`whitelist` 计数，以及该会话按工具族归因的 `toolChars` 字符总量，但**没有逐回执的族别字节**，
估算所需的投影分项仍然凑不出来——交付物里**没有任何工具能复算它**。

影子周也**不能**把这个区间变成实测百分比：影子报告只输出四个比例（见
[运维手册的影子周](operating.md#影子周)），没有总 token 分母；`boost status` 现在会报一个命中率和一个前缀回落计数，
但两者都不是「这段历史回放了多少 token」的分母；
区间要被实测取代，得等后续版本补上分母统计。

## 投影：截断 + 定位符 + spill

工具回执进入上下文之前，插件按工具族保留头尾，把中段换成可检索的落盘句柄。原文仍然可取回，
页脚给出路径。投影按固定阈值确定性执行，不产生逐次决策——同样的回执、同样的配置，裁法相同。

### 触发阈值与头尾窗口

每个工具族有三个数：`triggerChars`（超过才裁）、`headChars`、`tailChars`。默认值：

| 工具族 | `triggerChars` | `headChars` | `tailChars` |
|---|---|---|---|
| `read` | 3000 | 2000 | 500 |
| `grep` | 700 | 400 | 100 |
| `glob` | 700 | 400 | 100 |
| `bash` | 4000 | 2000 | 500 |
| `ssh`（`mcp__ssh__*`，如 `mcp__ssh__execute-command`） | 2000 | 1200 | 300 |

字符按 **Unicode 码点**计，不按 UTF-16 单元计：CJK 或 emoji 回执必须和 ASCII 回执在同一
“视觉长度”上裁，按码点切片也保证不会劈开代理对。`text.length` 只在 `truncate` 里做一次
便宜的前置粗筛——它是码点数的上界，`text.length <= triggerChars` 足以证明不该裁。

替换串是 **head line + head + 页脚 + tail + 3 个换行**。head line 的格式是
`[output N chars; showing first A and last B]`，数字按码点计；中段里形如 `[exit code: N]`、
`exit_code=…`、`is_error=…` 的标记行会被救回，附在 tail 之后，避免把退出码或错误标志裁掉。

### UTF-8 字节口径

三处长度用三种口径，不能混：

- **触发阈值与窗口**按 Unicode 码点计（上一节）。
- **256 KiB 投影上限**按 **UTF-8 字节**计（`Buffer.byteLength(text, 'utf8')`）。这是字节预算；
  若按 `text.length` 的 UTF-16 单元算，同一段 CJK 的字节数远大于单元数，上限会失真。
  超过 256 KiB 的回执**不投影**，原文完整进入历史。
- **页脚里的 `Omitted N bytes`** 也是**省略的 UTF-8 字节数**，不是字符数。取回完整性检查要
  在磁盘上量原文：`wc -c <locator>` 应等于页脚 N + 头部窗口字节数 + 尾部窗口字节数；窗口
  字节数要从可见投影里分别量，**不是** `headChars + tailChars`——中文/emoji 下两者不相等。
  具体步骤见 [`docs/RELEASE.md`](RELEASE.md) §3。

错误回执与超过 256 KiB 的回执不投影。错误回执是证据，先于任何裁剪判断被放行。

### 页脚与死区

页脚由宿主 `formatSpillNotice` 生成：68 字符 locator 加宿主固定的 66 字符 retrieval hint 下，
3 位省略字节数是 190 字符，5 位是 192 字符。grep/glob 默认 400+100 时：

```text
400 + 100 + 50（head line） + 190（页脚） + 3 = 743 > 700
```

5 位计数时页脚 192、head line 里的数字也各长一位，实测 747–749。于是刚过 700、约 743 以下的
回执会被 `truncate` 判定“可裁”，但 `projectApply` 组装后并不短于原文，直接返回原文——这是
**死区，不是净亏**。运行时的 `assembled.length >= text.length` 检查保证投影绝不会让回执变长；
要消除死区，把 `triggerChars` 提到至少这个和（例如 grep/glob 用 800），或缩小窗口。页脚长度
会随 locator 与数字位数浮动。

所以不变量不是 `triggerChars ≥ headChars + tailChars + 1`，而是要把 head line、页脚和换行都
算进去。窗口也不得大于等于触发阈值，否则会出现“触发了却裁不动”的区间。

### spill 与失败路径

`projection: 'on'` 时，完整原文在替换发生**之前**写入宿主的 spill 后端，页脚 locator 可以用
`read` / `grep` 取回。投影不会丢掉唯一副本；spill 写入失败就不替换（收据记
`projection-skipped:spill-failed`，页脚渲染失败记 `projection-skipped:footer-failed`；页脚
渲染器加载不到则记 `projection-skipped:no-footer`）。后端没有 `delete`，所以组装后若发现并不
更短，已经写出的 spill 会留在后端里无人引用，而模型拿回原文——这是死区的代价，不是数据丢失。

影子模式（`projection: 'shadow'`）不写 spill、不改模型可见 content，只计算“如果投影会省多少”。
它的定价只含 `(Omitted N bytes.)` 省略句，不含 locator/页脚全文，所以影子账的 `after` 是
**下界**；apply 路径在写入后还会再核对一次。

### 投影是截断，不是精炼

它保留头尾、丢掉中段；账本里的 before/after token 差量的是“变短”，不是“变相关”。被丢掉的
中段可能正是下一步决策要用的内容——`projection: 'on'` 下原文可经页脚 locator 取回，但取回要
花一次工具调用，且 v1 没有指标区分“精炼”与“误截”。这条边界在
[运维手册的已知限制](operating.md#已知限制与未交付项)里也记着。

## 替换：确定性只读

计划里重复的只读调用（`read` / `grep` / `glob`）若已有确定性证据满足守卫，直接提交，不再向
模型要一次决策；这省下的是一次模型回合（一次“慢速往返”）。多候选时用一个单标签选择器——
一次独立的辅助请求（`maxTokens` 512，另加其输入）——选一个。

这是对原始需求 2.2 的**收窄**：原需求要 Jev 对每个工具结果逐条打分、判断能否交给下一个工具，
v1 只做「同一回执上的多个候选里选一个」，不做逐条打分。这条收窄是**实现者的范围决定（E2）**，
不是用户裁决——澄清记录里**没有用户消息追认它**（见[澄清记录](superpowers/clarifications/2026-11-18-dsh-token-efficiency.md)
的 2.2 与「实现者决定」E2）。

### `$public` 绑定与守卫

对替换涉及的三个工具而言，计划里的 `$public` 参数绑定（把上一步回执里的值直接搬进下一步
参数）在实践中只对 `glob` 的单 token 输出有效；`read` 与 `grep` 的输出带行号或是裸路径，
标识符投影匹配不到，这些调用会退回模型。守卫读的是**原始规范化回执**，不是投影后的可见
content；投影在替换判定之后才施加。

### 多候选选择器

选择器**不读独立的模型配置**：它复用**边界请求**的 `provider` / `model` /
`reasoningEffort`（`src/index.ts` 的 `rememberRoute`，主来源是 `agent/pre-step` 的
`modelSelection`，`agent/request` 的解析结果只作回退），所以它不一定是廉价模型。要让它走
别的模型，只能在边界会话上换模型（宿主按 agent 选路由），或让计划只留一个候选（单候选
不调用选择器）。

### 影子期只记账

设计选择**影子优先**：先用一周只记账（不合成回合、不跳过调用，投影只记账不改内容），再决定
是否真的投影与替换。影子期写 `kind:'shadow'` 收据，替换决策只记录、不执行；多候选计划仍会
**真实调用一次选择器**。

**「什么都不改」并不成立**：`boost` 工具 schema（399 token）只要插件装配就常驻；只要有可见
工作区，协议段（379 token）还会注入系统提示——推荐配置下每请求固定成本 **778**。影子周不省
任何 token，它只产出四个比例；`selected + []` 下协议段为空，固定成本仍有 **399**。四个比例的
含义、影子报告的跑法与它不能回答什么，见[运维手册的影子周](operating.md#影子周)。

## 蒸馏：把回执压成一段可核验的正文

投影只能**截断**：头 2000 + 尾 500 是确定的，但它不知道这条回执里哪一行才是答案。蒸馏补这一半——
一个快速模型读整条回执，回答一个按族固定的问题（`bash`：「失败在哪、退出码是什么」），给回一段
正文加若干**逐字引用**。

它比投影多一层风险，所以有四道硬约束（见 [ADR 0001](adr/0001-receipt-pinned-distillation.md)）：

1. **钉住**：产物按 `(回执哈希, 问题哈希, 版本)` 落盘，重放只查表、不再调模型。这是它能存在的前提——
   如果每次渲染都重蒸一次，同一串历史字节会在不同请求里变成不同字节，provider 的前缀缓存整段作废
   （一次 19 万 token 前缀失配 ≈ 700 次投影省下的量）。
2. **可核验**：答案必须给出至少一条**原文的非空子串**，否则拒绝。零引用不是伪造，但不可核验。
3. **可回退**：关掉只影响之后的回执，已进入历史的字节不回滚。
4. **净赚才留**：正文 + 页脚按 UTF-8 字节必须**严格短于**同回执的截断视图，否则拒绝并钉墓碑
   （下次不再付一次调用）。

被拒、超时、失败一律**退回确定性截断**——关掉蒸馏时字节与没装这个功能完全一致，这条有测试钉住。
净赚门只看视图大小、**不看调用成本**，所以短会话里首次渲染可能净亏，长会话才靠重放摊薄。

## 准入：净节省阈值

替换不是“只要确定就做”。每个候选要过准入：**净节省严格大于阈值**才提交，打平不算赢。

```text
net = savedTokens − overheadTokens
准入 ⇔ net > admission.thresholdTokens
```

- `savedTokens` 是这次替换省下的模型往返的 token 数。HarnessMM 把被跳过的那次慢速往返记作
  `slowTokens`；本仓库不把它暴露成字段，准入函数拿到的是 `savedTokens` 与
  `overheadTokens` 两个数。
- `overheadTokens` 是多候选选择器的成本：输出上限 `selector.maxTokens`（默认 512）加按实际
  发送内容估算的输入（`maxTokens + estimate(input)`，不是固定 512）。
- `admission.thresholdTokens` 默认 **1024**，v1 是**全局单一**阈值，没有族维度；分族准入
  推迟到影子周呈现族间方差之后。
- **单步计划豁免**（`plan.steps.length === 1`，`src/hooks/post-execute.ts` 的 `admittedFor`）：
  计划只有一步时没有选择器可付，阈值不适用。不是“确定性 && 唯一候选”——多步计划即使只剩
  一个候选，仍要过阈值（`src/admission/ledger.ts` 的 `worthSubstituting`）。

每 turn 的替换步数上限是 `stepsPerTurn`（默认 8）。投影账的回放因子用 `horizon_steps`：
算不出会话历史均值时回落到 `horizonSteps`（默认 20），有历史时取
`min(horizonSteps, 最近 historyTurns 个 turn 的步数均值)`（`historyTurns` 默认 5）。`boost status`
按每条收据自己的 `horizon_steps` 重放；没有该字段的旧收据按当前 horizon 重放，并计入
`projection_horizon_reestimated`。

## 协议段与常驻开销

`fixedOverheadTokens` 是启动时实测的固定开销**合计**：协议段 379 + `boost` 工具 schema 399 =
778（本 checkout）。设计给这两项的预算是 **≤800 token/请求**（778 是实测）。它不是从
使用量里推断的：插件加载时用宿主的 `estimateSystemMessage` / `estimateToolsTokens` 测一次，
`boost status` 惰性 await 同一次测量，测量从不在请求路径上；没有 `chars/4` 回退。估算包不可达
时它是字符串 `'unknown'`，不是 778，也不是 0，`status.degraded` 同时带
`ERR_HOST_NO_ESTIMATOR`——伪造一个 0 会让审计读者分不清“真的为零”和“没测到”。

**哪个数字适用于当前请求取决于 scope**：

- `boost` 工具 schema（399）只要插件装配就常驻——`boost` 是唯一的 scope 豁免，始终留在工具
  声明里。
- 协议段（379）只在有可见工作区时注入；`selected + []` 下该段文本为空，**每请求固定开销实际
  是 399**。
- `status` 汇报的是合计 778（估算包不可达时是 `'unknown'`），不随 scope 翻转；工作区已选中
  时，778 就是当时的真实每请求开销。

778 相对每请求均值 195,531 约 **0.4%**；这就是“固定开销约 0.4%”的来源。长会话摊薄它，短会话
可能摊不回来——所以 0.4% 是聚合口径，不是每会话保底。

## 缓存与前缀稳定性

97.01% 的输入是缓存读。缓存匹配是**精确前缀**：任何早于断点的改动会让后缀全部失效。这是本
插件“追加式、到达即定形”的硬约束来源：

- 投影在回执**进入历史之前**决定并施加，改的是此后请求的追加段，不是已经发送过的前缀；它
  不回溯改写历史。
- 替换在步进判定时发生，同样只影响该步之后的追加内容。
- 因此插件不会为了省 token 去重写更早的上下文；那会让缓存后缀整体失效，代价远高于省下的量。

协议段的选择也是这个逻辑：设计把协议段做成**常驻且稳定**（D4），而不是“按需打开”。中途翻转
会让整段前缀失效并重算，代价高得多；所以推荐配置下每请求固定付 778，换来前缀稳定。
`selected + []` 是默认的惰性状态，协议段为空，固定成本降到 399。

账目全部按 raw token 计：cacheRead 也按 1 token 计，不打折、不算钱、不乘价格权重。3.5%–10.0%
的区间、0.4% 的净额和 97.01% 的缓存读占比都在同一口径下比较。

### 两条缓存护栏

`boost status` 报两个字段，用来让“前缀被悄悄打碎”这件事可见：

| 字段 | 含义 | 为什么这样取值 |
|---|---|---|
| `cache_hit_ratio` | 最近一次真实请求的 `cacheRead / (input + cacheRead)` | 没有样本时是 `null`，不是 `0`——`0` 会声称“什么都没命中”，而实际是没测到 |
| `prefix_drops` | 相邻请求间 `cacheRead` 低于上一次 `input + cacheRead` 的次数（`count`）与缺口合计（`tokens`） | 只看同一会话内的相邻两次；会话首个请求没有前驱，不计 |

**它是诊断，不是告警。** 回落有完全正当的原因：压缩会重写历史、provider 会淘汰缓存、请求可能换了路由。
这个数字存在的意义是让**没有解释的**回落暴露出来，而不是指控插件——插件自己只做追加式变换，不该造成回落。

**“只追加”靠结构，不靠测试**：插件唯一的改写点是回执进入历史之前（`tools/post-execute` 的返回），
没有任何代码路径会回头改已发出的消息。测试能钉住的是它的一半——可复现性：
`test/projection-determinism.test.ts` 断言同一输入渲染出同一串字节，且投影路径不出现
`Date.now` / `new Date` / `Math.random` / `randomUUID` / `randomBytes`。**它抓不到**「投影开始依赖
`Map` 插入顺序或环境变量」这类输入依赖，也抓不到「有人在别处回溯改写历史」——那两条靠审阅与
`AGENTS.md` 的约定。一次全量失配的代价大约相当于几百次投影省下的量，所以这条不变量写进约定、
也写进测试，两处都不省。
