发版链在 0.4.7 第一次真跑，被自己的第一步拦住（漏了版本号），补上后跑通。这一版修的是那条链暴露出来的问题：一次发布该在什么条件下拒绝、重试预算怎么定、以及「已发布」这个判断在传播窗口内为什么是假的。

**中文**

- 一个 tag 上完整门从两遍降到「显式一遍 + `prepublishOnly` 一遍」，并说清两遍各自买到什么：第一遍买的是失败时 step 名准确，第二遍才是验证要发布字节的那遍（`ci` 开头会删 `dist/` 重建）。
- 修 registry 传播窗口：`npm view` 与 `npm pack` 读同一份滞后元数据，所以「已发布则跳过」在发布后几分钟内是假的，重跑会先烧完整套门再撞 409。状态判定改为重试询问，重试预算从 5 分 30 秒（实测需求 5 分 03 秒）提到 20 分钟，最后一次失败后不再 `sleep`。
- 重跑分三态：未发布→发布；已发布无 release→只建 release（真正的恢复路径）；两者都有→拒绝。第三种只可能意味着 tag 被移动过，那会让 tag 的树与已发布字节不一致，而 release 页看起来完全正常。
- 新增 `workflow_dispatch`（`dry_run` 默认开）：只监听 tag 的 workflow 直到出事那天才第一次被执行，这条链此前正是如此。
- 新增「tag 指向的 commit 在 `main` 上」的前置检查：分支保护已让 main 的每次合并都过 `release-gate`，所以「树是绿的」等价于「commit 在 main 上」，这条挡的是另一种错——给功能分支打 tag。
- latest 断言改为比字节：只查 200 不够，另一个 release 的 asset 也会 200；现在同时断言 `gh release view --json tagName` 是这一版，且 `releases/latest/download/dsh-boost.tgz` 下载回来的 sha1 与 registry 的 `dist.shasum` 相同。
- release 已存在时刷新 body（`--notes-file` 只在 `create` 时被读，否则 `docs/releases/vX.md` 的修改永远到不了页面）。
- 安全面：`persist-credentials: false`，token 只出现在显式声明它的两步；补 `concurrency` 让同一 tag 的两个 run 不互撞；钉法检查从子串改成锚定正则（`0.4.80` 不再命中 `0.4.8`）。
- 文档：`docs/RELEASE.md` §6.0 重写（以 workflow 为准、重跑路径、tag 不可移动、`contents: write` 的真实范围），§7 清单里「`v*` tag 不会上传」这句与 §6.0 直接矛盾的旧话删掉；lockfile 断言的说法改成实际行为（每一条 `resolved` 都必须是 npmjs over https，空集也算失败）。
- 测试：`test/release-workflow.test.ts` 改为解析 YAML 而非匹配文本——文本断言会通过一个被注释掉的 step，也看不见哪一步带了哪个 env。按 id/name 定位 step，因为 `run` 里含注释，子串搜索曾让重试预算读到错的那一步。
- 去重：安装钉法原来有三份实现，删掉最弱的那份（「每个文件至少出现一次」，旁边一个过期的钉法它照样绿），保留 `test/docs-version.test.ts` 的强断言；`scripts/README.md` 曾被列进去却一个钉法都没有，空集通过，已移出。
- `docs/releases/v0.4.2.md` 的归属错误：`task` 字段是 0.4.4 才加的，0.4.2 的说明里写了它；GitHub 上那条已发布的 body 同步更正。
- 两处 banner 示例里写死的裸版本号改成 `<version>`：它们是 npm 的输出，不是安装钉法，钉到当前版本等于每发一版都要改，而它已经漂移过两次。

**English**

- The release chain ran for the first time on 0.4.7 and was stopped by its own first step (a missed version bump); it passed once fixed. This release fixes what that run exposed: when a release should refuse, how long to retry, and why "already published" is false during the propagation window.

- The full gate now runs twice per tag instead of three times — an explicit pass plus `prepublishOnly` — and the docs say what each pass buys: the first gives a step name that says "gate", the second is the one that validates the published bytes (`ci` deletes and rebuilds `dist/`).
- Fixed the registry propagation window: `npm view` and `npm pack` read the same lagging metadata, so "skip if published" is false for minutes after a publish, and a re-run burns the whole gate before hitting a 409. The state probe now retries, the budget went from 5m30s (measured need: 5m03s) to 20 minutes, and no `sleep` runs after the final attempt.
- Re-runs distinguish three states: unpublished → publish; published without a release → create only the release (the real recovery path); both present → refuse. The third can only mean the tag moved, which leaves the tagged tree and the published bytes disagreeing while the release page looks fine.
- Added `workflow_dispatch` (`dry_run` on by default): a tag-only workflow is untested until the day it matters, and this chain was exactly that.
- Added a precondition that the tagged commit is on `main`: branch protection already makes every merge pass `release-gate`, so "the tree is green" reduces to "the commit is on main", and this catches the other mistake — tagging a feature branch.
- The latest assertion now compares bytes: a 200 is not enough, since another release's asset also answers 200. It also asserts `gh release view --json tagName` names this version and that the downloaded sha1 matches the registry's `dist.shasum`.
- An existing release gets its body refreshed (`--notes-file` is only read by `create`, so edits to `docs/releases/vX.md` never reached the page).
- Hardening: `persist-credentials: false`, the token only in the two steps that declare it, `concurrency` so two runs for one tag cannot race, and the pin check anchored so `0.4.80` no longer matches `0.4.8`.
- Docs: `docs/RELEASE.md` §6.0 rewritten (the workflow is authoritative, re-run paths, tags are immutable, what `contents: write` really grants), and the §7 checklist line claiming `v*` tags are not uploaded — contradicting §6.0 — is gone. The lockfile claim now states the actual assertion: every `resolved` must be npmjs over https, and an empty set fails.
- Tests: `test/release-workflow.test.ts` parses the YAML instead of matching text — a text assertion passes on a commented-out step and cannot see which step carries which env. Steps are located by id or name, because `run` blocks contain comments and a substring search once read the retry budget from the wrong step.
- Deduplication: the install pins had three implementations; the weakest is gone (it asserted "each file mentions the pin at least once", which stayed green beside a stale pin). `scripts/README.md` was listed with no pin at all — an empty set passing as coverage — and is no longer listed.
- Corrected an attribution error in `docs/releases/v0.4.2.md`: the `task` field landed in 0.4.4, not 0.4.2. The published GitHub Release body was corrected too.
- Two banner examples pinned a literal version; they are npm output, not install pins, so pinning them meant editing them every release — and they had drifted twice. They now read `<version>`.
