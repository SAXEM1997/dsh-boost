**中文**

设置页的数据路由补上宿主自己的准入检查。`webServer.register` 不跑准入——它把整条响应的生命周期交给 handler，所以路由不自己调 `connection.admit(req)` 就是裸的：能连上端口的东西都能读写 `scope.json`。

- 两道闸串联：先问宿主要说法（浏览器 cookie / API token），再走本插件的同源栅栏。此前只有栅栏，管得住跨站与 DNS rebinding，管不住同机上的另一个进程。
- 新码 `ERR_HTTP_UNAUTHORIZED`（401，响应体只有这个码，不含任何状态）；403 仍归 `ERR_HTTP_FORBIDDEN`。
- 宿主没有 `connection` 服务时不改变行为；那道检查抛错按拒绝处理，不按放行。
- 这个缺陷是插件市场评审指出的。声明属实，已接上——但这一版的接线是错的（挂载时快照，晚激活即永久无准入），见 0.4.6。
- 环境事实：本机 `dsh-client-connection` 的 `isAuthenticated()` 被 `/* dsh-noauth */` 打桩成恒真，所以在这个宿主上准入只到栅栏那一层。

**English**

The settings page's data route now asks the host's own admission check. `webServer.register` runs no admission — it hands the whole response to the handler — so a route that does not call `connection.admit(req)` itself is bare: anything that can reach the port can read and write `scope.json`.

- Two gates in series: the host's verdict first (browser cookie or API token), then this plugin's same-origin fence. Previously only the fence, which stops cross-site requests and DNS rebinding but not another process on the same machine.
- New code `ERR_HTTP_UNAUTHORIZED` (401, body carries only the code and no state); 403 stays `ERR_HTTP_FORBIDDEN`.
- Behaviour is unchanged on hosts with no `connection` service; a check that throws counts as a refusal, not as permission.
- The defect was found by the plugin-marketplace review. The report was accurate and the call is now wired — but this version's wiring is wrong (a snapshot taken at mount, so late activation means no admission at all). See 0.4.6.
- Environment fact: on this machine `dsh-client-connection`'s `isAuthenticated()` is stubbed to `true` by `/* dsh-noauth */`, so admission here only reaches the fence layer.
