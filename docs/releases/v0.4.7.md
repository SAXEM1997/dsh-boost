**中文**

发版从「手工跑命令」变成「打 tag」。`v*` tag 推上去后，CI 跑完整条门、发布到 npm、建 GitHub Release，并把 tarball 以两个名字挂上去。

- 新增 `.github/workflows/release.yml`：tag 与 `package.json` 版本必须一致、`docs/releases/v<版本>.md` 必须存在、四份文档的安装钉法必须写这个版本，然后跑 `npm run ci` + `verify:package -- --prebuilt` + `verify:negatives`。
- 发布后取**已发布的** tarball 与 registry 的 `dist.shasum` 比对，再建 release 并挂 `dsh-boost-<版本>.tgz`（存档）与 `dsh-boost.tgz`（`releases/latest/download/` 解析到的名字）。
- 重跑安全：版本已在 registry 上就跳过发布，release 用 `view || create`，asset 用 `--clobber`——最需要重试的失败（registry 传播延迟）发生在不可逆那一步之后。
- `ci.yml` 不再监听 tag：tag 归 `release.yml`，两个都监听会让一次发版跑两遍套件。
- 补齐 `v0.4.0`–`v0.4.6` 七个版本的 GitHub Release，说明取自 CHANGELOG 并按中英双语写进 `docs/releases/`；更早的版本只有 tag。
- 新增 `test/release-workflow.test.ts` 盯住上面三条不变式（trigger、门的内容、本版本有双语说明），并把「四份文档都写当前版本」从发布门提前到 `npm test`。
- 第一次打 tag 就抓到了这条链的第一类静默失效：`package.json` 还是 0.4.6 而 tag 是 `v0.4.7`，workflow 在第一步就红，没有发出任何东西。

**English**

Releasing moves from "run the commands by hand" to "push a tag". Once a `v*` tag is pushed, CI runs the whole gate, publishes to npm, creates the GitHub Release, and attaches the tarball under two names.

- New `.github/workflows/release.yml`: the tag must equal the `package.json` version, `docs/releases/v<version>.md` must exist, and the install pins in four documents must name this version — then `npm run ci` + `verify:package -- --prebuilt` + `verify:negatives`.
- After publishing it takes the **published** tarball, compares it against the registry's `dist.shasum`, then creates the release and attaches `dsh-boost-<version>.tgz` (the archive) and `dsh-boost.tgz` (what `releases/latest/download/` resolves to).
- Re-running is safe: an already-published version is skipped, the release is `view || create`, the asset is uploaded with `--clobber` — the failure most likely to need a retry (registry propagation) happens after the irreversible step.
- `ci.yml` no longer listens for tags: tags belong to `release.yml`, and both listening would run the suite twice per release.
- Backfilled GitHub Releases for `v0.4.0`–`v0.4.6` from the CHANGELOG, written bilingually into `docs/releases/`; older versions stay tag-only.
- New `test/release-workflow.test.ts` pins those three invariants (trigger, gate contents, bilingual notes for this version) and moves "all four docs name the current version" from the release gate into `npm test`.
- The first tag push caught the first silent failure this chain exists for: `package.json` still said 0.4.6 while the tag was `v0.4.7`, so the workflow went red at step one and published nothing.
