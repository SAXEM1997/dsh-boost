# 澄清记录：dsh-boost（2026-11-18）

> 本文件记录 Phase 0 的需求澄清结果与用户裁决，供 Phase 2 拆任务时对照。
> 设计正文见 [设计稿](../specs/2026-11-18-dsh-token-efficiency-design.md)。

## 用户原始需求（m00001，逐字要点）

1. 注入 [HarnessMM](https://github.com/YuhuaJiang2002/HarnessMM) 的主要功能，允许调研拆解并澄清"做到什么程度、哪些部分"。
2. 让 DSH agent 一次调用多个工具（类 PTC）；每轮工具结果交给 Jev 决策打分，判断能否交给下一个工具，还是回大模型；并研究组合工具调用顺序由谁定。
3. 做成提高 DSH token 效率的插件：既省 token（减少模型介入次数与范围），又把冗余工具调用精简，使上下文更精炼高质。

## 澄清后的结论（逐条对照）

| 原始需求 | 澄清结果 | 依据 |
|---|---|---|
| 1. 注入 HarnessMM | **v1 移植的是扁平候选银行 + 确定性守卫（GDR）+ 单候选提交（CCS）+ 闭集选择器（Jev）**；**没有移植 EDG 的图与链**：HarnessMM 的候选带 `predecessor_id`，替换后位置推进（`ref-harnessmm/dsh-plugin/harnessmm-desktop/lib/controller.mjs:507-521`），本插件的计划是扁平、每回执一次性的候选列表，源码里没有 `predecessor_id`（`src/gate/plan.ts:54-57`；`src/hooks/post-execute.ts` 的 `decideSubstitution` 文档注释，one-shot per receipt）。desktop 形态推二期 | 逐项对照 `src/` 与 `controller.mjs`；参照仓库自带可运行 DSH 插件 |
| 2.1 一次调多个工具（PTC） | **显式排除，二期** | 实测每步只调 1 个工具占 79.8%，一期杠杆不在批量 |
| 2.2 Jev 给"能否交给下个工具"打分 | **收窄为"多候选中选一个"**，不做逐条打分 | 下一步参数逐字来自上一步回执只有 7.2%（45,082 个可判定调用的下界；2026-11-20 按调用级口径复算，初稿的 7.1%/45,745 是字符串叶口径）；打分要读回执，成本倒挂 |
| 2.3 顺序由谁定 | **未交付调研、也未裁决——记录为开放缺口**：用户要求调研"如何决定组合工具的调用顺序（用 Jev 决策还是大模型一开始定好）"，但没有任何交付物回答它——`docs/research/2026-11-18-three-tier-delegation.md` 覆盖提取 / span 校验 / 路由阈值 / 乐观执行 / 缓存经济 / 压缩，**没有定序权威一节**，也没有比较"选择器定序"与"计划冻结定序"的实验。代码事实：计划是每回执一次性（`src/hooks/post-execute.ts` 的 `decideSubstitution` 文档注释），主模型对下一次调用写新块；定序权威是主模型逐步决定，Jev 只在已声明候选里选一个、无权加步骤或改序。**"2.3 被 2.1 的排除吸收"是实现者的判断，不是用户裁决**：裁决 #9 只覆盖 2.1 与 2.2。它不阻塞 v1 的理由仅限——2.3 是多工具组合问题，而 v1 已按 2.1 的裁决排除多工具组合，故 v1 没有需要定序的路径；这不等于调研已完成，也不等于用户已同意收窄。 | 代码：`src/hooks/post-execute.ts` 的 `decideSubstitution` 注释；研究文档未涉及；无对比实验；裁决 #9 只覆盖 2.1/2.2 |
| 3. 提 token 效率 | **两个杠杆**：追加式投影（全部工具）+ 只读替换（read/grep/glob） | v1 **投影侧毛额约 0.8%**，扣每请求固定开销约 0.4% 后**净保底约 0.4%**；替换账 2.70% 是上限、不计入保底；**目标上界 10.0%**（含替换账上限）。按 raw `totalTokens`。**"更高质"未测量**：v1 没有任务完成率/推翻率 instrumentation，"质量不降"只是设计意图，不是已验证结论 |

## 实现者决定（非用户裁决，用户可否决）

| # | 决定 | 依据 | 用户裁决状态 |
|---|---|---|---|
| E1 | **影子结果不决定发布**：即使影子周两账合计只有 5%，v1 也按正常版本发布（设计稿 §3 的 ②）。影子周只用于修正预期数字、为替换侧是否开启提供标签，不作发布门 | 软件复算不出 §3 的 ex-ante 区间：`scripts/shadow-report.mjs` 只出四个比例（`saveableRatio` / `byFamily` / `candidateRecall` / `retrievalUpperBound`），没有总 token 分母，也不分桶；影子周的分母结构性不完整——`retrievalUpperBound` 在影子期恒为 0（分子只统计 `projection:'on'` 的取回，影子期投影收据是 `kind:'shadow'`），`saveableRatio` 的分母是门的决策收据数，不是请求数或 token 数。拿它当发布门，等于用一台测不出净额的仪器裁决发布 | 用户裁决了"影子期一周可接受"（裁决 #2，m00234），**没有**裁决"影子结果是否决定发布"。本条是实现者的设计决定，未经用户裁决；README 的同一表述应同样理解为设计决定 |

## 显式排除范围（实现阶段不得重新捡起）

| 排除项 | 理由 | 何时重议 |
|---|---|---|
| PTC / 多工具并行 | 每步单工具占 79.8%，收益不在批量 | 影子期拿到批量步真实占比后 |
| Jev 逐条打分 / 全局路由 | 值传递只 7.2%，且打分要读回执 | 值传递实测明显高于 7.2% 时 |
| 调用去重 / 合并 | 与"替换"是两件事，先测重复率 | **v1 没有可计算的重开条件**：`scripts/shadow-report.mjs` 不统计重复率，收据只覆盖门的决策（替换/投影），不覆盖全部工具调用，因此没有重复率的分母。维护者若要用一手数据判断，只能在会话样本上手工按 `tool + 规范化 args` 哈希分组、以样本内**可判定的相邻调用**为分母统计重复占比，并先定义"重复"是同一 turn 内还是跨 turn；这个数字不由 v1 产出 |
| 模型蒸馏（快速模型压缩回执） | LLM 压缩器在短任务 +24~94% token | 二期 |
| bash 的替换 | `sandbox_permissions` 只能升不能降 | read-only sandbox 验收通过后 |
| desktop 形态 | — | 二期 |
