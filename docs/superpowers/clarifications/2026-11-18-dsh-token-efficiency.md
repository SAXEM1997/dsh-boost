# 澄清记录：dsh-boost（2026-11-18）

> 本文件记录 Phase 0 的需求澄清结果与用户裁决，供 Phase 2 拆任务时对照。
> 设计正文见 [设计稿](../specs/2026-11-18-dsh-token-efficiency-design.md)。

## 用户原始需求（m00001，逐字要点）

1. 注入 [HarnessMM](https://github.com/YuhuaJiang2002/HarnessMM) 的主要功能，允许调研拆解并澄清"做到什么程度、哪些部分"。
2. 让 DSH agent 一次调用多个工具（类 PTC）；每轮工具结果交给 Jev 决策打分，判断能否交给下一个工具，还是回大模型；并研究组合工具调用顺序由谁定。
3. 做成提高 DSH token 效率的插件：既省 token（减少模型介入次数与范围），又把冗余工具调用精简，使上下文更精炼高质。

## 澄清后的结论（逐条对照）

| 原始需求 | 澄清结果 | 依据 |
|---|---|---|
| 1. 注入 HarnessMM | **v1 移植的是扁平候选银行 + 确定性守卫（GDR）+ 单候选提交（CCS）+ 闭集选择器（Jev）**；**没有移植 EDG 的图与链**：HarnessMM 的候选带 `predecessor_id`，替换后位置推进（`ref-harnessmm/dsh-plugin/harnessmm-desktop/lib/controller.mjs:507-521`），本插件的计划是扁平、每回执一次性的候选列表，源码里没有 `predecessor_id`（`src/gate/plan.ts:54-57`、`src/hooks/post-execute.ts:1299-1305`）。desktop 形态推二期 | 逐项对照 `src/` 与 `controller.mjs`；参照仓库自带可运行 DSH 插件 |
| 2.1 一次调多个工具（PTC） | **显式排除，二期** | 实测每步只调 1 个工具占 80.0%，一期杠杆不在批量 |
| 2.2 Jev 给"能否交给下个工具"打分 | **收窄为"多候选中选一个"**，不做逐条打分 | 下一步参数逐字来自上一步回执只有 7.2%（45,082 个可判定调用的下界；2026-11-20 按调用级口径复算，初稿的 7.1%/45,745 是字符串叶口径）；打分要读回执，成本倒挂 |
| 2.3 顺序由谁定 | **代码里没有"计划时冻结"**：计划是每回执一次性（`src/hooks/post-execute.ts:1299-1305`），主模型对下一次调用写新块；定序权威是主模型逐步决定，Jev 只在已声明候选里选一个、无权加步骤或改序。**"让选择器定序会退化成第二主模型"是未经验证的设计直觉**：研究文档（`docs/research/2026-11-18-three-tier-delegation.md`）未涉及定序权威，也没有实验比较"选择器定序"与"计划冻结定序"。需求 2.3 不在 line 34 的补记内（该补记只覆盖 2.1/2.2）；可辩护的立场是：2.3 属于多工具组合，v1 已按 2.1 的裁决排除，无剩余阻塞项。 | 代码：`src/hooks/post-execute.ts:1299-1305`；研究文档未涉及；无对比实验 |
| 3. 提 token 效率 | **两个杠杆**：追加式投影（全部工具）+ 只读替换（read/grep/glob） | v1 **投影侧毛额约 0.8%**，扣每请求固定开销约 0.4% 后**净保底约 0.4%**；替换账 2.70% 是上限、不计入保底；**目标上界 10.0%**（含替换账上限）。按 raw `totalTokens`。**"更高质"未测量**：v1 没有任务完成率/推翻率 instrumentation，"质量不降"只是设计意图，不是已验证结论 |
