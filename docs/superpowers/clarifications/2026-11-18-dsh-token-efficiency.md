# 澄清记录：dsh-boost（2026-11-18）

> 本文件记录 Phase 0 的需求澄清结果与用户裁决，供 Phase 2 拆任务时对照。
> 设计正文见 [设计稿](../specs/2026-11-18-dsh-token-efficiency-design.md)。

## 用户原始需求（m00001，逐字要点）

1. 注入 [HarnessMM](https://github.com/YuhuaJiang2002/HarnessMM) 的主要功能，允许调研拆解并澄清"做到什么程度、哪些部分"。
2. 让 DSH agent 一次调用多个工具（类 PTC）；每轮工具结果交给 Jev 决策打分，判断能否交给下一个工具，还是回大模型；并研究组合工具调用顺序由谁定。
3. 做成提高 DSH token 效率的插件：既省 token（减少模型介入次数与范围），又把冗余工具调用精简，使上下文更精炼高质。

## 澄清后的结论（逐条对照）

| 原始需求 | 澄清结果 | 依据 |
|---|---|---|
| 1. 注入 HarnessMM | **v1 注入四机制**：计划银行（EDG）、确定性守卫（GDR）、单候选提交（CCS）、闭集选择器（Jev）。desktop 形态推二期 | 参照仓库自带可运行 DSH 插件，四机制齐备 |
| 2.1 一次调多个工具（PTC） | **显式排除，二期** | 实测每步只调 1 个工具占 80.0%，一期杠杆不在批量 |
| 2.2 Jev 给"能否交给下个工具"打分 | **收窄为"多候选中选一个"**，不做逐条打分 | 下一步参数逐字来自上一步回执只有 7.1%（45,745 个可判定位置的下界）；打分要读回执，成本倒挂 |
| 2.3 顺序由谁定 | **主模型在计划时冻结**，Jev 无权定序 | 让选择器定序会退化成第二主模型 |
| 3. 提 token 效率 | **两个杠杆**：追加式投影（全部工具）+ 只读替换（read/grep/glob） | v1 预期 3.5%（保底）– 10.0%（上界），按 raw `totalTokens` |

## 显式排除范围（实现阶段不得重新捡起）

| 排除项 | 理由 | 何时重议 |
|---|---|---|
| PTC / 多工具并行 | 每步单工具占 80%，收益不在批量 | 影子期拿到批量步真实占比后 |
| Jev 逐条打分 / 全局路由 | 值传递只 7.1%，且打分要读回执 | 值传递实测明显高于 7.1% 时 |
| 调用去重 / 合并 | 与"替换"是两件事，先测重复率 | 影子期统计出重复率后 |
| 模型蒸馏（快速模型压缩回执） | LLM 压缩器在短任务 +24~94% token | 二期 |
| bash 的替换 | `sandbox_permissions` 只能升不能降 | read-only sandbox 验收通过后 |
| desktop 形态 | — | 二期 |
