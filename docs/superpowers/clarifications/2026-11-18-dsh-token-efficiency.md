# 澄清记录：dsh-boost（2026-11-18）

> 本文件记录 Phase 0 的需求澄清结果、用户裁决与实现者决定，供 Phase 2 拆任务时对照。
> 设计正文见 [设计稿](../specs/2026-11-18-dsh-token-efficiency-design.md)。

## 用户原始需求（m00001，逐字要点）

1. 注入 [HarnessMM](https://github.com/YuhuaJiang2002/HarnessMM) 的主要功能，允许调研拆解并澄清"做到什么程度、哪些部分"。
2. 让 DSH agent 一次调用多个工具（类 PTC）；每轮工具结果交给 Jev 决策打分，判断能否交给下一个工具，还是回大模型；并研究组合工具调用顺序由谁定。
3. 做成提高 DSH token 效率的插件：既省 token（减少模型介入次数与范围），又把冗余工具调用精简，使上下文更精炼高质。

## 澄清后的结论（逐条对照）

| 原始需求 | 澄清结果 | 依据 |
|---|---|---|
| 1. 注入 HarnessMM | **v1 移植的是扁平候选银行 + 确定性守卫（GDR）+ 单候选提交（CCS）+ 闭集选择器（Jev）**；**没有移植 EDG 的图与链**：HarnessMM 的候选带 `predecessor_id`，替换后位置推进（`ref-harnessmm/dsh-plugin/harnessmm-desktop/lib/controller.mjs:507-521`），本插件的计划是扁平、每回执一次性的候选列表，源码里没有 `predecessor_id`（`src/gate/plan.ts:54-57`；`src/hooks/post-execute.ts` 的 `decideSubstitution` 文档注释，one-shot per receipt）。desktop 形态推二期；**RSI 循环未移植**：HarnessMM 的 recursive self-improvement 用训练反馈细化 companion prompts / context settings / adapter rules，并在验证集上从冻结候选里选一个（`ref-harnessmm/README.md:56-58`），本插件没有训练/选择生命周期，`src/` 无对应代码 | 逐项对照 `src/` 与 `controller.mjs`；参照仓库自带可运行 DSH 插件 |
| 2.1 一次调多个工具（PTC） | **收窄为二期；这是为实现范围而推迟，不是被证明没有价值**：PTC / 批量派发未做，v1 只做"一次一个"的只读替换。 | 每步**恰好 1 个**工具占 79.8%（43,201/54,141）；其余 20.2% 是 100−79.8 的非单工具步——按快照复算，其中 **16.9%（9,137 步）带 ≥2 个调用**（2 个 15.8%、≥3 1.1%），另有 3.3%（1,803 步）零调用（`scripts/session-snapshot.json` 的 `callsPerStep`）。用户明确要求批量派发，非单工具步就是它的作用面；一期先落地只读替换 + 投影，PTC 留二期，重启条件是影子期拿到批量步的真实占比与收益标签，而不是"79.8% 已证明不需要批量"。 |
| 2.2 Jev 给"能否交给下个工具"打分 | **收窄为"多候选中选一个"**，不做逐条打分 | 7.2%（3,249/45,082）是**可判定的下一步调用里、参数含上一步回执逐字 span** 的比例（`design:36`）：只统计逐字出现的片段，提取/改写（取字段、换格式）不计入。所以它是"逐字值传递"的下界，不是"这条结果能否作为下一个工具的输入"的比例——后者没有测量。成本论证也比初稿弱：已交付的选择器本来就把回执最多 1,200 字符送进 prompt（`src/hooks/post-execute.ts:162` 的 `SELECTOR_RECEIPT_MAX_CHARS`；`src/selector/jev.ts:150-155` 的 `selectorPromptText`），逐条打分的新增成本主要是打分输出与额外往返，不是"从零读一份回执"。收窄仍成立，但理由是范围与收益不确定性，不是 7.2% 证明了值传递不存在。 |
| 2.3 顺序由谁定 | **未交付调研——开放缺口，且不被 PTC 的推迟覆盖**：用户要求调研"如何决定组合工具的调用顺序（用 Jev 决策还是大模型一开始定好）"，但没有任何交付物回答它。`docs/research/2026-11-18-three-tier-delegation.md:37` 有最相关的证据：ReWOO / LLMCompiler 都是**先声明整个计划、步骤之间不再问模型**（执行是确定性的），但 `:74-85` 的 implications 从未把它应用到"定序权威"上，也没有比较"选择器定序"与"计划冻结定序"的实验。代码事实：计划是每回执一次性（`src/hooks/post-execute.ts` 的 `decideSubstitution` 注释），主模型对下一次调用写新块；Jev 只在已声明候选里选一个、无权加步骤或改序。**PTC 讲的是"一次派发多个调用"，定序讲的是"谁决定下一个调用"——两者不是同一件事**：即使不做 PTC，定序问题仍然存在，只是 v1 把权威放在主模型逐步决定上。这是实现现状，不是用户裁决，也不是已完成的调研。 | 代码：`src/hooks/post-execute.ts` 的 `decideSubstitution` 注释；`docs/research/2026-11-18-three-tier-delegation.md:37` 有 plan-then-execute 证据、`:74-85` 未应用；无对比实验；无用户裁决（E2 只覆盖 2.1/2.2） |
| 3. 提 token 效率 | **两个杠杆**：追加式投影（全部工具）+ 只读替换（read/grep/glob） | v1 **投影侧毛额约 0.8%**；扣每请求固定开销约 0.4% 后，**300 个最长会话上的聚合净额约 0.4%**——这不是每会话保底（短会话可能倒亏，§6.1）。替换账 2.70% 是 token 份额的上限，只有实际发生替换才计入，不能预先加到任何保底里；**目标上界 10.0%**（含替换账上限）。**3.5% 是离线区间的低端，不是 floor**：它把上限 2.70% 加进了低端。按 raw `totalTokens`。**"更高质"未测量**：v1 没有任务完成率/推翻率 instrumentation，"质量不降"只是设计意图，不是已验证结论 |

## 显式排除范围（实现阶段不得重新捡起）

| 排除项 | 理由 | 何时重议 |
|---|---|---|
| PTC / 多工具并行 | 为实现范围推迟，不是证明批量无价值：79.8% 是单工具步，但 20.2% 不是（16.9% 带 ≥2 调用、3.3% 零调用）；用户明确要求批量派发 | 影子期拿到批量步真实占比与收益标签后 |
